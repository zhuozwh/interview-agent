# v0.5.1：Windows 启动入口热修复

## 失败证据

执行日期：2026-08-27。

用户按 v0.5.0 的最短路径访问聊天页时，服务处于停止状态。执行仓库根目录的 `start.cmd` 后，Windows PowerShell 5.1 在 `scripts/start.ps1` 第 80、147、150 行附近报告意外 `}` 和字符串缺少结束引号，服务没有监听 `http://127.0.0.1:8000/`。

源码本身以 UTF-8 正确读取时语法完整；两个 `.ps1` 文件首字节直接是 `[`，没有 UTF-8 BOM。Windows PowerShell 5.1 的 `-File` 会按旧系统代码页解释无 BOM 文件，中文字符串因此被误解码，部分字节序列破坏引号配对。v0.5.0 的 AST 检查显式按 UTF-8 读取文本，没有覆盖用户真正经过的解码入口。

修复编码后，从当前 Codex 宿主执行真正的 `cmd.exe /d /c start.cmd -NoBrowser` 又复现第二个失败：宿主环境同时存在 `Path` 和 `PATH`，Windows PowerShell 5.1 的 `Start-Process` 把环境复制到不区分大小写的字典时报告重复键，服务仍未启动。这一问题不会出现在显式从 PowerShell 7 父进程直接运行 `.ps1` 的替代路径中，因此必须保留 `.cmd` 入口验收。

另外，两个 `.cmd` 原本在 PowerShell 失败后执行 `pause`，却没有提前保存失败退出码；非交互环境可能最终观察到 `pause` 的成功状态，降低错误的可归因性。

## 第一性原理

目标用户执行的是“双击批处理文件”，而不是“用指定编码读取后再做 AST 检查”。因此可用性的验收边界必须从真实入口开始：

1. 系统自带 Windows PowerShell 5.1 必须按预期解码中文脚本；
2. 启动失败必须保留原始非零退出码，并把可理解错误留在窗口中；
3. 启动成功必须得到 loopback HTTP 200 首页和 `health=ok`；
4. 停止必须得到退出码 0、删除 PID 记录并关闭健康地址；
5. 整个启停验收不得提问、加载 Embedding、建立索引或调用远端 LLM。

## 修复

- `scripts/start.ps1` 和 `scripts/stop.ps1` 使用带 BOM 的 UTF-8，兼容 Windows PowerShell 5.1，同时保持中文注释和错误信息；
- `scripts/start.ps1` 在创建服务子进程前把当前脚本进程内大小写重复的 `Path` / `PATH` 归一为单个 `Path`；不修改用户、系统或持久环境变量；
- `start.cmd` 和 `stop.cmd` 在调用后立即保存 `%errorlevel%`，只在失败时暂停，最后显式 `exit /b` 返回原始退出码；
- `start.cmd` 透传可选参数，允许自动化使用 `-NoBrowser` 验证同一个批处理入口；
- 新增回归，硬性检查两个脚本的 BOM 和两个批处理文件的退出码协议。

| `GET /health` | `200`、`status=ok` |

编码回归先直接读取原始字节，确认两个 PowerShell 脚本均以 `EF BB BF` 开头。真实启动先使用系统 `powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts\start.ps1 -NoBrowser`，随后必须再使用 `cmd.exe /d /c start.cmd -NoBrowser` 覆盖批处理继承的真实环境；不能以 PowerShell 7 或自行解码的 AST 替身代替。停止直接使用 `cmd.exe /d /c stop.cmd`。

## 变化边界与剩余风险

本补丁不修改聊天 UI、会话历史 schema、检索、阈值、Top-K、Router、RAG、提示词、回答接受条件或引用校验，也不接触真实 Vault 内容。运行时文件仍位于 Git 忽略目录。

Windows PowerShell 5.1 与当前 Windows 代码页组合已真实验证；PowerShell 7 继续能识别 UTF-8 BOM。后续入口测试不能再只报告 AST 通过，必须至少保留 BOM 契约，并在发布前运行一次系统 `powershell.exe -File` 启停闭环。
