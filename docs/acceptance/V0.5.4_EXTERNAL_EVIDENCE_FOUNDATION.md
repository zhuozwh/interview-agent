# v0.5.4：外部证据基础验收

## 第一性原理与范围

执行日期：2026-08-31。

使用者仍是本机单个面试准备者。真实问题不是“让 Agent 什么都能上网”，而是在本地资料没有覆盖普通技术知识、或用户想交叉核对时，能够清楚知道将向谁发送什么，并把外部结果当作独立、未核验的参考，而不是伪装成自己的经历或本地证据。

最短完整用户路径是：先完成一轮普通技术知识问答，点击“联网补充”，在本机看到实际外发查询；若真实提供方已配置，再看到提供方、查询和最多来源数并明确确认；服务最多搜索一次；页面用独立 `[W1]` 卡片展示来源域名、标题和摘要。用户无需操作 FastAPI `/docs`，也不会因为本地无证据而自动触发网络。

需要持久化的状态没有增加。外部查询、搜索 ID、提供方结果、标题、摘要和 `[W]` 卡片只存在于当前页面内存，不进入 SQLite、Chroma、日志正文、`localStorage`、`sessionStorage`、本地引用核验或 Agent 上下文。刷新、切换会话、新建会话或删除当前会话即丢失；因此生命周期就是当前页面，没有单独删除动作。真实 Vault 和 Markdown 继续只读，运行时数据边界不变。

失败边界是：只有自包含的普通知识问题可预览；项目、简历、面试记录、第一人称个人上下文、本地资料指代、明显批量外带、联系方式、本机路径和常见凭据均停止。发生脱敏时不能静默发送。确认文本变化、提供方未配置/异常、候选超量或类型错误、危险 URL 和非法文本都失败关闭。外部失败不能覆盖本地回答、触发 `/ask` 重试或放宽 Phase 2 证据阈值。

可验证验收标准：默认装配零真实网络；预览不调用提供方；配置合成提供方后确认查询精确匹配且只调用一次；个人/本地问题在提供方前停止；外部 `[W]` 与本地 `[S]` 分区并标注来源未核验；候选只作为有界纯文本，危险 URL 不可点击；响应不缓存、结果不落库；Phase 2 检索、Router、RAG、提示词、答案接受和引用完整性零变化；默认系统、回归和对抗测试只使用合成数据。

本版本是用户明确要求提前进入 Phase 3 的外部证据协议与界面基础，对原规范 Phase 5 做最小例外。真实搜索提供方、endpoint/密钥、网页抓取、外部内容进入 LLM、事实合成、缓存、写入和自动搜索仍留在后续阶段，不能据此视为已授权。

## 实现

- 新增 `ControlledExternalSearchService`。预览在本机归一化查询，复用既有个人数据脱敏和检索前策略，再增加常见凭据、第一人称个人上下文及本地指代门禁；默认 `provider=None`。
- 提供方协议只接受一条有界查询和最多 5 个结果，规定单次调用且实现内部不得自动重试。服务端在调用前重新计算策略，并要求 `confirmed_query` 与当前预览逐字一致。
- 新增 `POST /api/external-search/preview` 和 `POST /api/external-search`。Pydantic 严格拒绝额外字段；所有成功和业务错误响应带 `Cache-Control: no-store` 与 `Pragma: no-cache`；底层异常和凭据不进入公开错误。
- 不可信候选最多接收 25 个、展示 5 个；标题 240 字符、摘要 900 字符、URL 2048 字符。链接只允许规范公共 HTTPS 域名，拒绝用户名/密码、自定义端口、所有字面 IP、localhost、`.local`、`.internal`、敏感查询参数、控制字符、反斜杠和重复 URL，并移除 fragment。
- 界面只在状态为 `success` 或 `no_evidence` 的 `knowledge_question` 轮次展示入口。先请求预览；未配置 provider 时立即说明本次没有联网；配置后通过原生确认框展示提供方、实际查询和最多来源数，确认后才发出唯一搜索请求。
- 外部卡片只用 `createElement` 和 `textContent`；链接要求 HTTPS，使用新标签页、`noopener noreferrer` 和 `no-referrer`。来源类型明确写成“提供方标记”，区域同时提示“来源未核验”。
- 切换、新建或删除当前会话会递增请求序号，使旧的在途响应失效。没有定时器、自动重试、浏览器持久化或把外部 payload 附加到 `/ask` 的路径。

## 对抗测试、失败归因与修复

| 场景 | 预期或发现 | 结果 |
|---|---|---:|
| 项目、简历、面试记录、批量联系方式 | 必须留在本地，提供方调用数为 0 | 通过 |
| 邮箱、手机号、本机路径 | 生成替换后的安全预览但禁止发送 | 通过 |
| `api_key`、access token、`sk-`、Bearer、GitHub token、密码 | 初版通用脱敏器覆盖不足；增加外部边界专用高确定性凭据模式 | 修复后通过 |
| “我在上一家公司…”、“根据刚才回答…” | 初版 namespace 只能识别明确项目/简历标记；增加个人上下文和本地指代停止 | 修复后通过 |
| 预览后篡改确认查询 | 409，提供方调用数为 0 | 通过 |
| provider 未配置或抛出含密钥异常 | 503 固定中文错误，不泄漏底层正文 | 通过 |
| provider 返回 list、错误对象或 26 个候选 | 集合类型与数量失败关闭 | 通过 |
| HTTP、localhost、字面 IP、凭据 URL、自定义端口、敏感 query、空白字符 | 初版只覆盖部分 URL；补齐公共域、凭据与链接数据边界 | 修复后通过 |
| 同一 URL 不同 fragment | 去重并去除 fragment | 通过 |
| 标题/摘要包含 `<script>` | 服务保留为文本，浏览器只用 `textContent` | 通过 |
| 提供方自报 `official_documentation` | 初版标签容易被理解为平台背书；改为“提供方标记、来源未核验” | 修复后通过 |
| 切换会话时旧请求返回 | 请求序号失效，不把结果写入新会话 | 通过 |
| 结果持久化或进入 `/ask` | 无 SQLite/浏览器存储字段，无外部 payload 合并入口 | 通过 |

安全收紧过程中曾因域名长度条件缺少逻辑连接导致 Python 测试收集时报语法错误。该错误在任何冷启动或发布操作前被针对性套件立即发现并修复；修复后同一套件为 **34 passed**。这说明当前发布门禁能拦截不可运行构件，但也保留为过程证据，不把“最终测试通过”包装成一次完成。

## 验证结果

最终默认离线全回归为 **388 passed、5 skipped**，比 v0.5.3 增加 27 个通过项且没有新增 skip。五个 skip 原样为：当前 Windows 账户不能创建符号链接、显式真实本地 Embedding、显式真实 Phase 2 端到端 Embedding、显式真实远端 LLM 端到端和既有真实检索/LLM 验收入口。Node `app.js` 语法、Python `compileall` 和 `git diff --check` 均通过。

版本审计发现当前 editable 安装元数据仍自报 0.5.2，虽然仓库此前已是 v0.5.3。首次用 `pip install --no-deps -e .` 刷新时，pip 的隔离构建仍尝试查询 setuptools；受限网络在连接阶段阻止，未完成下载或安装。随后显式增加 `--no-build-isolation`，只复用当前环境构建工具，成功安装本地 editable 0.5.4；最终 `importlib.metadata.version("interview-agent")` 返回 `0.5.4`。该问题只影响本机开发环境的包元数据，不改变源码或生产数据，但证明离线发布步骤不能只依赖 `--no-deps`。

在 8012 端口以 `SESSION_HISTORY_ENABLED=false` 和隔离数据库路径冷启动当前包：首页 200 且包含外部资料隐私说明，`/health=ok`；`RAII 官方资料` 的预览在本机成功，`provider_configured=false`；直接搜索稳定返回 503“尚未配置”；隔离 SQLite 未创建。停止后 8012 不再监听。

整个开发与验收没有调用 `/ask`、没有加载或下载 Embedding、没有建立索引、没有读取真实 Markdown/Vault 正文、没有配置或调用真实搜索提供方，也没有产生新的真实远端 LLM 请求、token 或费用。合成 provider 只返回 `example.com` 等虚构公开来源。

## 指标与剩余风险

- Phase 2 固定检索指标未重跑或重算，因为生产 Retrieval、阈值、Top-K、Router、RAG、提示词、答案接受和引用校验均未修改；v0.4.5/v0.4.6 的匿名指标继续有效。新增 27 项只证明外部证据产品与安全边界，不代表回答召回率或正确率提高。
- v0.5.2 记录的 notes `0.5850` 假阳性仍存在。外部入口不能被用来删除该样本、放宽阈值或把搜索摘要混入本地回答制造绿灯。
- 常见个人数据和凭据检测不是完整 DLP；姓名、护照、银行卡、企业内部代号和任意自由文本秘密仍可能漏检。当前控制依赖只允许自包含知识问题、屏幕展示实际查询和用户确认。涉及个人/公司内部上下文时应重新表述为不含私密事实的通用技术问题，或保持本地处理。
- 原生确认框是产品交互，不是 API 认证。拥有 loopback 调用能力的进程未来可直接调用搜索 API；服务端仍会执行策略和精确确认文本校验，但不能证明真人点击。当前默认无 provider，因此无费用或外发；真实接入前应决定是否增加一次性确认许可、调用速率和费用上限。
- v0.5.4 不抓取结果页面，所以服务器没有 SSRF 或重定向链；但用户点击外链后进入浏览器和目标站点信任边界。公共 HTTPS、无引用来源标头和域名展示降低风险，不能证明页面安全、域名信誉或内容真实性。
- 真实 provider 适配器仍需设计固定 endpoint、`trust_env`/代理、DNS 重绑定、重定向、超时、响应字节、并发、重试、查询日志/保留、密钥错误净化和费用审计。不得把当前接口测试当成这些控制已经完成。
- 外部摘要没有进入 LLM，因此系统只展示来源，不会自动生成“融合答案”。如果后续需要合成，必须重新确认模型、endpoint、调用次数、输入/输出 token、费用，以及允许把哪些外部内容与哪些本地证据共同外发。

## 下一决策点

v0.5.5 若继续，应先由用户选择真实搜索提供方，并明确：provider 与 endpoint、单次/每日最大请求数、是否允许重试、费用上限、实际外发查询范围、供应方数据保留、允许来源域、结果字节与超时、是否只展示来源还是允许一次 LLM 合成。没有这些确认时，v0.5.4 保持默认离线是完整且可用的安全状态。

## 发布结论

v0.5.4 达到“先把外部证据做成可理解、可确认、可隔离、可验证的产品边界，同时保持零默认网络和 Phase 2 零退化”的目标。真实搜索效果尚未产生，也没有伪装成已经联网。发布前仍需检查工作树只包含本里程碑预期文件，再提交、创建详细 annotated tag 并推送。
