## 失败案例与反思纠错

### 测试集纠错

- `N07` 最初只允许《虚函数表》作为期望来源。实际 Top-1《虚函数调用过程》和 Top-2《虚函数》都明确解释了虚表指针、虚函数表和动态绑定。人工回读原文后，将三篇都标记为可接受来源，纠正了过窄标签；检索代码和问题未修改。
- `P02` 的 Config 问题在 notes 中会合法命中哈希表和 key 相关资料；`P08` 的 Buffer/TCP 半包问题在 notes 中存在真实粘包知识。它们不适合作为“错误 namespace 必须 no_results”的样本，已从跨域负例中移除。
- 纠错后保留的 3 个跨 namespace 探针全部通过，冷/暖运行结果一致。

### 真实失败

- `P03`：目标 Logger 文档原始排名为 Top-1，但最高分约 `0.569796`，低于项目 Tool 当前统一阈值 `0.58`，因此返回 `no_results`。
- `P04`：Reactor 目标文档进入 Top-5，但相关片段最高约 `0.537974`；当前阈值同样拒绝全部证据。
- `HN11`：询问项目是否使用 Kubernetes HPA 自动扩缩容时，语义向量把“自动扩缩容”错误关联到 Buffer 扩容资料，最高分约 `0.625121`，超过阈值，导致 Tool 返回证据并调用确定性 LLM 替身。

这三项不是通过修改问题或临时调低阈值解决的验收器错误。它们证明项目与 notes 共用 `0.58` 阈值的依据不足，并暴露否定式“是否实现某功能”对语义近邻的误接受风险。

## Phase 2 决策

当前预基线触发：

- `hard_negative_rejection_below_0_95`；
- `critical_positive_failed`。

这些证据足以在 v0.4.0 评估：

- 分 namespace 阈值校准；
- 项目事实存在性和否定式问题的拒答策略；
- 项目资料的切分、召回和排序；
- 是否需要关键词与向量混合检索或重排序。

本次没有实施上述优化。v0.3.x 只保留真实问题集、验收器和匿名基线。

## 正式三源验收前置条件

1. 用户手工提供独立、只读且不与现有源重叠的 resume Markdown 目录。
2. 在本机问题集中增加至少 6 个匿名 resume 正例、隐私样本、硬负例和跨 namespace 样本。
3. 更新精确 `ALLOWED_DATA_DIRECTORIES`，保持 `LLM_API_KEY` 为空。
4. 重新运行冷启动、暖启动、Vault 前后指纹、SQLite、引用、脱敏和拒答检查。
5. 只有正式报告生成后，才能决定 v0.3.1 的最终发布/tag 状态。
