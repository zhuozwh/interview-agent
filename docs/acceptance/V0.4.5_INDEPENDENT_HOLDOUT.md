# v0.4.5：用户独立冻结的真实 Vault holdout

## 结论

执行日期：2026-08-13。

用户在任何 v0.4.5 评测运行前，于 Git 忽略的本机文件中独立写下 6 个 holdout case。系统没有替用户生成、同义改写或根据结果调整这些问题；只在首次运行前把三条来源路径从 Vault 根相对格式机械转换为各 namespace 根相对格式。冻结输入在转换、评测和复核后的 SHA-256 均为 `72509ed2b7790d382c52c639c6d65be0bc92ed88f2f057dfcb414f4588f9efe4`。

首次正式 calibration/holdout 运行即通过。没有删除失败样本、扩大可接受来源、修改阈值、调整 Top-K 或调用远端 LLM。

## 问题集构成与隐私

- calibration：从 v0.3.1 冻结 45-case 基线原样选取 6 个既有 case，覆盖三域正例、三域硬负例和跨 namespace；
- holdout：6 个由用户独立写下的 case，覆盖 notes 正例、projects 同域一轮指代正例、resume 当前轮跨域覆盖正例，以及 notes/projects/resume 各一个硬负例；
- 总计 12 case、19 probe，其中 holdout 6 case、9 probe；
- holdout 当前问题与旧 45-case 的规范化精确重复数为 0；
- 正例相对路径在首次运行前全部验证存在；
- schema v3 的 calibration/holdout 分割、三域正负例、硬负例和跨 namespace 覆盖校验通过。

真实问题正文、上一问、个人事实映射、相对来源路径和明细报告均保存在 Git 忽略的 `acceptance_local/v0.4.5/`，不进入仓库、tag 或远端。提交文档只记录匿名计数、哈希和聚合指标。

- 只使用本地 Embedding，`LLM_API_KEY` 显式覆盖为空白，DeepSeek 调用 0 次；
- Vault 运行前后快照一致，`vault_unchanged=true`；
- SQLite 边界、LLM 替身隐私边界和第二次索引同步幂等性通过；
- schema v3 规范化 case manifest SHA-256：`2c13996a87328d181a7853e3afde1d730f26370fe037f69a85f242b347799c01`；
- 本次数据源快照 manifest SHA-256：`9513d4b88c0866250cb9e345b37331883c75d15e43232727a0f8c5232ec2cdc4`。

数据源 manifest 只证明本次运行前后使用同一快照，不声称用户在不同版本验收之间从未自行编辑 Vault。

## 第一性原理判断

独立 holdout 没有暴露召回失败、阈值误杀、排序错误、事实存在性错误或策略错误，因此本阶段没有证据支持引入混合检索、扩大候选池或独立重排模型。尤其是阈值单独使用仍存在安全误接受，说明当前结果来自“固定 namespace + 独立阈值 + 事实证据门控 + 候选内轻量排序”的组合，而不是继续调低或调高某个分数。

## 剩余风险

- holdout 规模仍小，每个 namespace 仅一个独立正例和一个独立硬负例，100% 指标的统计置信度有限；
- 问题由产品使用者独立编写，但不是外部双盲评测；
- 一轮上下文只验证显式上一问题，不覆盖长期记忆、自动摘要或多 Tool 规划；
- 完整输出侧语义 DLP 按当前单机单用户范围继续暂缓；
- 未来新增真实资料类型、改变 Embedding 模型或升级 Router 时，应另建新的、运行前冻结的 holdout，而不是反复改写本集。
