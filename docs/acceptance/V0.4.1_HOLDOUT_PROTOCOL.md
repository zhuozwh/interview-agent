# v0.4.1：独立留出评测协议与泛化检查

## 目标与起点

执行日期：2026-08-11。

本阶段从已发布并推送的 annotated `v0.4.0` 开始。目标不是继续调低阈值，而是验证 v0.4.0 的策略是否能在冻结后新增的匿名场景上泛化，并阻止 calibration 与 holdout 之间的数据泄漏。

## schema v3 协议

- 每个 case 必须声明 `evaluation_split=calibration|holdout`；
- 两个 split 都必须分别覆盖 notes、projects、resume 的正例和负例；
- 两个 split 都必须包含硬负例和跨 namespace 探针；
- 总体平均值不能替代 split 独立质量门槛；任一 holdout 关键正例失败都会产生 `holdout_*` trigger；
- `threshold_only_best` 只允许从 calibration 计算；
- calibration 选出的阈值会原样应用到 holdout，报告不计算“最佳 holdout 阈值”；
- 空 probes case 被拒绝，避免用只测路由的空样本稀释指标；
- Router、正例 grounding、引用完整性、Agent 正例闭环和拒答率全部进入显式门槛。

schema v1/v2 继续作为 `legacy` 协议兼容原 45-case 真实基线，manifest 不变。

## 冻结匿名对抗集

仓库内 `tests/fixtures/phase2_v041` 在 v0.4.0 发布之后建立，包含 8 个 case 和 13 个 probe：

- calibration：三域正例、两项跨域探针、一项简历批量外带硬负例；
- holdout：三域正例、三项跨域探针、一项项目合取事实硬负例；
- “列出所有邮箱服务协议”必须作为 notes 技术问题通过，不能被“邮箱”子串误杀；
- “同时使用 Reactor 和 Kafka”在证据只有 Reactor 时必须拒绝；
- 一轮 `previous_question` 仍需重新检索并建立当前引用白名单。

两个 split 的 Router、Hit@1、Hit@5、MRR、硬负例拒绝、跨 namespace 拒绝、Agent 边界和引用完整性均为 100%。纯阈值从 calibration 迁移到项目 holdout 时仍产生一个硬负例误接受，权重代价为 4；策略感知结果代价为 0。这是保留事实策略、而不是继续调阈值的独立证据。

## 回归中发现并纠正的问题

1. 本机忽略的 `.env` 仍显式设置旧 projects/resume 阈值 `0.58`。首次回归因此复现旧基线失败；验收随后使用 v0.4.0 已发布阈值 `0.535/0.56` 和隔离运行时复跑。代码和 `.env.example` 正确，用户本机 `.env` 未被自动修改。
2. 初版对抗修复把所有多锚点问题都要求为全覆盖，导致真实固定集 P04 被事实门槛误拒绝。最终规则只对“同时、均使用、全部使用”等明确合取事实和结构化属性对要求全部锚点；普通多主题问题保留部分证据，但提示词必须逐项标记未确认内容。
3. 初版测试错误要求纯阈值迁移在 holdout 也达到零代价。真实结果代价 4 正是阈值不足的证据，因此改为同时断言纯阈值失败和策略感知通过，未删除或放宽失败样本。

## 人工冻结点与剩余风险

- 仓库夹具证明评测协议和策略对匿名新场景有效，但不能冒充独立真实 Vault 留出集；后者需要用户本地人工编写并冻结 schema v3 问题，不能从旧问题机械改写。
- 用户本机 `.env` 的 projects/resume 阈值仍需手动从 `0.58` 更新为 `0.535/0.56`，避免运行时覆盖已发布默认值。
- 事实锚点仍是确定性词面充分性规则，不是开放域语义蕴含模型。
- 真实 DeepSeek 未调用。执行前仍需用户确认模型、endpoint、调用次数、token 上限、预计费用和允许外发证据范围；首轮不得发送真实 resume 片段。
